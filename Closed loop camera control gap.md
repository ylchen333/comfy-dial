# Nobody yet closes the camera-control loop

The claim is **partly confirmed**. As of October 16, 2026, no ComfyUI workflow, custom node pack, Comfy Hub app, open-source studio, or commercial product found in this research runs the full loop: author camera and motion as geometry, render control signals, generate N candidates, automatically measure 3D camera-trajectory or point-track adherence against the authored target, then rank and regenerate failing segments. Two parts of the wording go too far. **"Nobody measures camera adherence" is false inside ComfyUI.** The small, unadopted shotdrift node already checks 2D pan, zoom, and roll against a preset label and outputs a reroll boolean. **"Research measures camera accuracy" understates the research.** Pose-based rotation and translation error is already used as an RL training reward (CamVerse, Geo-Align) and, since September 30, as a test-time camera reward inside a particle-filter sampler (PartiCam). The defensible version is narrower: *no released tool combines authored 3D camera/track geometry, IC-LoRA control rendering, N finished candidates, measured RotErr/TransErr/FOV and track error against that authored target, and verifier-driven ranking plus per-segment regeneration.* The stack is technically feasible on open weights for the Oct 15–30 "Open Source Higgsfield" build window. The pieces are LTX-2.5 with the LTX-2.3 depth or motion-track IC-LoRAs, fan-out through `@comfyorg/sdk`, and scoring with core-ComfyUI Depth Anything 3 Small/Base, which is Apache-2.0 and emits extrinsics and intrinsics. Four risks need day-one tests: Comfy Cloud support for the IC-LoRA nodes, low Cloud API concurrency, how robust pose recovery is on generated video, and the unproven dolly zoom. The verifier itself is the novel component, and Claude Code has no existing skill for it, so it should be the first thing built and the first thing tested.

## Partly confirmed: every step has prior art, but no tool runs the verified loop

The claim combines three assertions, and each holds to a different degree. "LTX ships control adapters" is **true with a caveat**. The Union-Control (depth, canny, pose) and Motion-Track IC-LoRAs exist only as **LTX-2.3 checkpoints**, which Lightricks' official LTX-2.5 workflows reuse unchanged ([LTX docs: IC-LoRA adapters](https://docs.ltx.io/open-source-model/integration-tools/ic-lo-ra-adapters); [LTX docs: Motion Control](https://docs.ltx.io/open-source-model/feature-guides/structural-control/motion-control)). "Research measures camera accuracy" is **true but incomplete**. CameraCtrl, CameraCtrl II, and RealCam-I2V use RotErr and TransErr only as benchmark metrics ([CameraCtrl](https://arxiv.org/pdf/2404.02101); [RealCam-I2V](https://arxiv.org/pdf/2502.10059)). Newer work already puts that signal inside optimization: CamVerse computes **segment-level** rotation and translation error after scale alignment as a GRPO reward ([arXiv 2512.02870](https://arxiv.org/pdf/2512.02870v1)), and PartiCam resamples candidates with a camera reward at inference time ([arXiv 2609.39504](https://arxiv.org/html/2609.39504)). "No app combines them" **survives** as an app-level claim, but only if "measure adherence" means 3D trajectory or track error against an authored target, not a 2D motion-type check.

The table names the nearest prior art for each loop step. The pattern is that each step is covered somewhere, while no single tool covers more than two steps with a geometric verifier.

The precise restatement to defend in a demo is this: *"Authoring tools stop at compile time, best-of-N tools judge aesthetics, and camera-error verifiers live inside research training loops. This app is the first to diff the generated clip's recovered 3D camera and re-tracked points against the trajectory the user drew, then rank candidates and regenerate only the segments that drift."* Every clause of that sentence is supported by the evidence above. The unqualified "nobody closes the loop" is the one a knowledgeable judge could puncture, because shotdrift and PartiCam both exist.

## Comfy's own apps and 6,000 node packs stop at "generate takes, human picks"

Comfy's own reference apps for this challenge share one design: generate takes, then a human picks. The **Re-shoot** app (open PR, "no production path yet") runs depth analysis and takes on a dedicated CrossView Comfy API deployment, offers a WebGL2 depth-warp preview and a keyframe timeline, and returns each take with "Seed is random by default". It describes no scoring, ranking, or partial regeneration ([PR #18910](https://github.com/Comfy-Org/ComfyUI_frontend/pull/18910)). **Cinematic Studio** is a full-screen editor with a takes strip where take selection is manual ([PR #20638](https://github.com/Comfy-Org/ComfyUI_frontend/pull/20638)). The challenge page lists both as Hub examples and marks Openjutsu "Coming soon" ([Open Source Higgsfield](https://comfy.org/open-source-higgsfield/)). Among **691 official workflow templates**, a keyword scan found camera and motion templates (Wan Fun Camera, Wan ATI, Wan-Move, LTX-2.3 IC-LoRA, Qwen multi-angle) but no template that scores, ranks, or verifies. The only "pick" templates are manual contact-sheet grids ([workflow_templates index.json](https://raw.githubusercontent.com/Comfy-Org/workflow_templates/main/templates/index.json)). Even Lightricks' own Motion Control guide offers IC-LoRA strength as the only adherence control and says adherence is judged by reviewing the output ([LTX docs](https://docs.ltx.io/open-source-model/feature-guides/structural-control/motion-control)).

The most telling finding is the **direction of use**. ComfyUI already has pose-recovery nodes for VGGT ([VVL VideoCamera](https://comfy.icu/extension/wTechArtist__ComfyUI_VVL_VideoCamera_Advanced)), Depth Anything 3 ([DA3 Parse Camera Pose](https://www.runcomfy.com/comfyui-nodes/ComfyUI-DepthAnythingV3/da3-parse-camera-pose)), DUSt3R, DPVO inside OmniCam, and CoTracker for tracks. Every one of them runs **upstream**, extracting a camera from reference footage or building tracks to drive Wan ATI. None runs **downstream** to check a generated clip against its command. camera-comfyUI is the clearest near-miss: it has trajectory authoring and a VGGT `VideoPoseEstimator` in the same pack, but no node compares the two ([camera-comfyUI](https://github.com/Alexankharin/camera-comfyUI)). A keyword scan of the **6,022-entry ComfyUI-Manager list** found no ViPE, MegaSaM, MASt3R, or SpatialTracker packs and no RotErr/TransErr implementation ([Manager list](https://raw.githubusercontent.com/Comfy-Org/ComfyUI-Manager/main/custom-node-list.json)).

Two neighbours deserve explicit credit in the submission, because they show the gap has been noticed. shotdrift states the problem directly: "Generative video is given a camera move and is under no obligation to deliver it. The usual check is a person watching sixty clips" ([shotdrift-comfyui](https://github.com/Syamjith-NK/shotdrift-comfyui)). It has 0 stars and 5 commits, and it is absent from both the Registry and the Manager list. CachedSearch exposes a pluggable `CS_VERIFIER` interface ("any node that outputs a CS_VERIFIER object with a score(images, prompt) -> float method works") ([ComfyUI-CachedSearch](https://github.com/shreshthsaini/ComfyUI-CachedSearch)). A camera-adherence verifier written to that interface would plug into an existing best-of-N sampler and show ecosystem awareness. OmniCam is the competitor most likely to close the gap first. Its author already has a camera solver and a canonical MotionScene, so "solve the generated clip and diff it" is a small step that has not been taken as of October 16. Reusing OmniCam's MotionScene or LTX-track JSON as the commanded path would sharpen the story further.

## Higgsfield and its rivals leave the user as the verifier

No commercial product checked automatically scores camera-path adherence or ranks outputs by it. Higgsfield's help center describes Cinema Studio as per-shot camera, lens, focal length, aperture, and named moves. In 4.0, built on Seedance 2.5, it adds a Director's Panel with genre, era, and tempo controls, camera bodies, up to 50 references, and 30-second clips. It never mentions multiple outputs, adherence checks, or reranking ([Higgsfield help: Cinema Studio](https://higgsfield.ai/creator-hub/help-center/tools/how-do-i-use-cinema-studio); [Cinema Studio 4.0 blog](https://higgsfield.ai/blog/cinema-studio-4-0)). Higgsfield's own build story says quality control was human: camera operators were asked "does this look AI to you?" and "Whatever failed that check was out." The same page quotes a user getting good results in the "first batch. Fourth at worst", which implies rerolling ([Inside Higgsfield #1](https://higgsfield.ai/blog/how-we-built-cinema-studio)). Reviews gathered earlier in this research report the same failure mode: compound camera moves break, users reroll 3–5 times per keeper, and Higgsfield's CEO has called generation "a slot machine". The Google Flow/Veo forum shows the cost in credits, with "75 credits spent on an 8-second clip that was still unusable" and "camera mismatch" listed among continuity problems ([Google AI Developers forum](https://discuss.ai.google.dev/t/veo-flow-generation-issues-lost-credits-consistency-problems-and-excessive-failed-generations/147374)).

Two caveats keep this from being a clean refutation of Higgsfield. First, the same Higgsfield page mentions "an anti-slop camera pipeline" without detail, so some internal automatic filtering cannot be ruled out. It is simply not exposed to users. Second, Higgsfield's September 2026 **3D Jutsu** (prompt-driven 3D scene building) was seen only as a one-line description. If it pairs 3D scene geometry with a camera path, it would be a commercial step-1 competitor, and its verification behaviour is unknown. Other open apps are further from the loop. Open-Higgsfield-AI turns camera choices into prompt modifiers, so it has no geometric camera to measure against ([README](https://raw.githubusercontent.com/Anil-matcha/Open-Higgsfield-AI/main/README.md)). Autodesk Flow Studio tracks live-action footage for VFX export, not generated video ([Autodesk](https://www.autodesk.com/products/flow-studio/features)). Runway, Luma, Kling, LTX Studio, and Google Flow primary docs were not read, and that gap matters most for the novelty claim.

The product framing follows from this. Higgsfield sells a camera vocabulary; this entry would sell a **camera guarantee with a number attached**: "4 of 8 takes held the dolly within 3° and 5% of path length; segment 2 drifted and was regenerated." The "slot machine" admission is the right foil for the demo.

## The open-weights stack is buildable in two weeks, with four hard risks

The recommended pipeline uses only components with documented ComfyUI paths. The browser studio renders the authored camera into a **depth pass** and/or **projected 2D point tracks** in Three.js, skipping LTX's Video Depth Anything preprocessor. The backend submits an API-format graph with **LTX-2.5 distilled + `ltx-2.3-22b-ic-lora-union-control-ref0.5`**, which is Lightricks' own documented 2.5 pairing, or the Motion-Track IC-LoRA via `LTXAddVideoICLoRAGuide`. Frame counts follow the "1 + multiple of 8" rule, for example 121 frames ≈ 4.8 s at 25 fps ([LTX Union Control](https://docs-dev.ltx.io/open-source-model/feature-guides/structural-control/union-control); [LTX Motion Control](https://docs.ltx.io/open-source-model/feature-guides/structural-control/motion-control)). Lightricks says "the large majority" of 2.3 IC-LoRAs run on 2.5 unchanged, and staff confirmed the union LoRA works ([HF LTX-2.5](https://huggingface.co/Lightricks/LTX-2.5); [HF discussion #5](https://huggingface.co/Lightricks/LTX-2.5/discussions/5)). Adherence strength is set per run with LoRA strength, a 0–1 `attention_strength`, and an optional spatial mask ([LTX IC-LoRA guide](https://docs.ltx.io/open-source-model/usage-guides/ic-lo-ra)). That gives the regeneration step a real control to adjust beyond the seed: a failing segment can be retried at higher strength.

The Node 22 backend fits the SDK closely. `@comfyorg/sdk` loads API-format JSON, calls `setInput`, uploads hash-deduplicated assets, and provides `submit()` and `job.events()`. It targets Comfy Cloud, a Comfy API deployment, or self-hosted ComfyUI via `comfy-api-proxy` at `http://127.0.0.1:8189`, so the same code covers "run locally" and "try it" ([Comfy SDK docs](https://docs.comfy.org/development/api-development/sdks.md)). There is no batch call, so N candidates means N `submit()` calls with distinct seeds. Two SDK details shape the job layer. **Idempotency keys reject duplicates rather than replaying them** (`422 idempotency_key_reuse`), and a plain retry loop "creates duplicate jobs and charges". So the backend must persist `{key → jobId}` before awaiting and recover through `client.jobs.get`. Cloud API access requires a paid subscription, and concurrency is **1 / 3 / 5 / 25** jobs for Standard / Creator / Pro / Team, with up to 100 queued ([Comfy pricing](https://comfy.org/pricing.md)). On Creator, N=8 runs three at a time, and the scoring graph competes for the same slots. Comfy Router's `ltx/ltx-2-5-pro` takes text-only parameters with no IC-LoRA or video conditioning, so it cannot serve the control loop ([Router LTX-2.5 Pro](https://docs.comfy.org/development/comfy-router/models/ltx/ltx-2-5-pro/code.md)). It would also break the Open Weights Only rule, which forbids "partner nodes or APIs" ([challenge page](https://comfy.org/open-source-higgsfield/)).

The verifier fits inside ComfyUI too. **Core ComfyUI now ships Depth Anything 3** (`LoadDA3Model`, `DA3Inference`). In `mode=multiview` it returns per-view `extrinsics` and `intrinsics`, but only for the **Small and Base models, which are Apache-2.0**. Large and Giant are CC BY-NC 4.0 ([DA3Inference docs](https://docs.comfy.org/built-in-nodes/DA3Inference.md); [DA3 README](https://raw.githubusercontent.com/ByteDance-Seed/Depth-Anything-3/main/README.md)). Scoring can therefore be a second ComfyUI graph submitted through the same SDK path, which keeps "everything runs through Comfy". The metric layer should follow published protocols:

1. Make both trajectories relative to frame 0.
2. Umeyama/Sim(3)-align the recovered camera centers to the authored ones, as in CameraCtrl II's ATE alignment ([CameraCtrl II](https://arxiv.org/pdf/2503.10592)).
3. Report per-frame-normalized RotErr, TransErr normalized by path length, and RealCam-I2V-style CamMC ([RealCam-I2V](https://arxiv.org/pdf/2502.10059)).
4. Add a non-standard **FOV-trajectory error** from the recovered intrinsics.
5. Score segment-wise, which is CamVerse's finding: clip-level reward does worse ([arXiv 2512.02870](https://arxiv.org/pdf/2512.02870v1)).
6. For track adherence, report endpoint error between authored and re-tracked points, the Motion Prompting definition ([arXiv 2412.02700](https://arxiv.org/pdf/2412.02700)).

Implement Umeyama directly, about 30 lines, rather than importing evo, which is **GPL-3.0-or-later** ([PyPI evo](https://www.pypi.org/project/evo/1.24.0/)). For the re-tracker, use TAPIR/BootsTAP, whose LICENSE file is Apache-2.0 ([tapnet LICENSE](https://raw.githubusercontent.com/google-deepmind/tapnet/main/LICENSE)). **CoTracker3 and SpatialTracker v2 are CC BY-NC** ([CoTracker LICENSE](https://raw.githubusercontent.com/facebookresearch/co-tracker/main/LICENSE.md); [SpaTrackerV2 LICENSE](https://raw.githubusercontent.com/henry123-boy/SpaTrackerV2/main/LICENSE.txt)), even though CoTracker already has ComfyUI nodes. COLMAP 4/GLOMAP (BSD) is a cross-check, not the primary scorer, because COLMAP is unstable on short clips and CameraCtrl had to discard failures ([CameraCtrl](https://arxiv.org/pdf/2404.02101)).

Four risks are serious enough to test in the first two days.

**Cloud node availability.** Comfy Cloud lists ComfyUI-LTXVideo as preinstalled with 64 nodes. The visible listing omits `LTXICLoRALoaderModelOnly`, `LTXAddVideoICLoRAGuide`, `LTXVDrawTracks`, and `LTXVCropGuides`, while the Union-Control model page says to "access it through Comfy Cloud" ([Cloud supported nodes](https://comfy.org/cloud/supported-nodes/ComfyUI-LTXVideo.md); [model page](https://comfy.org/p/supported-models/ltx-2-3-22b-ic-lora-union-control-ref0-5.md)). The fallback is local ComfyUI behind `comfy-api-proxy`, which requires only a `COMFY_BASE_URL` change.

**Headless motion tracks.** The Sparse Track Editor is an interactive widget. The API graph will likely have to inject track JSON into the widget value or pass a pre-rendered track-guide video in place of `LTXVDrawTracks`. This is unverified until the node's input schema is read.

**Verifier robustness.** No benchmark of DA3 pose accuracy on AI-generated video was found, and the multiview output's tensor format and units are undocumented. Flicker, morphing, and moving subjects will corrupt some solves. Report a "pose-solve failed" penalty rather than silently dropping candidates. Fall back to rotation-only scoring for pans and tilts, where scale alignment is degenerate.

**Segment regeneration.** No prior art was found for this step. LTX first/last-frame and extend workflows are the likely primitives: regenerate segment k conditioned on the last good frame of segment k−1 and the matching slice of the control pass. Seam continuity is untested.

The **dolly zoom** is the highest-reward, highest-risk demo shot. No published evidence shows LTX or any open depth-controlled video model reproducing one. The only paper evidence is qualitative, on AnimateDiff ([MotionMaster](https://arxiv.org/pdf/2404.15789)). A rendered depth sequence encodes the effect geometrically, but per-clip normalized relative depth may wash it out. Measuring it requires the per-frame intrinsics that DA3 multiview provides. Use the dolly zoom as a headline test only after a simple push-in and orbit pass the verifier.

On licensing for the Open Weights Only category: LTX-2.x weights are downloadable under the **LTX-2.x Community License**, which allows free commercial use below $10M revenue. That license is not OSI-approved ([HF LTX-2.5](https://huggingface.co/Lightricks/LTX-2.5)). It fits the plain meaning of "open weights models only", and the repo's own code can still carry MIT or Apache. Avoid reusing CozyClay code, because AGPL-3.0 would impose copyleft on a network-served app ([CozyClay LICENSE](https://raw.githubusercontent.com/NomaDamas/CozyClay/main/LICENSE)). LTX as the core model also qualifies the entry for the **$2,000 cash LTX VFX bonus**. Most Innovative, Open Weights Only, and that bonus are the natural targets for this entry. The official page says the Most Innovative demo video "must explain why the submission is innovative". The step-coverage table above is that explanation. The current page does not say whether one entry can win both a main prize and a bonus. Note also that the older "Comfy Dev Platform Challenge" coverage (Oct 19 deadline, $2,000 *in API credits*, "Best OSS-only workflow") predates the relaunch and should not be used ([comfyui-wiki, Oct 1](https://comfyui-wiki.com/en/news/2026-10-01-comfy-dev-platform-challenge)).

## Existing Comfy, 3D and testing skills speed up the build, but the verifier skill must be written

The verifier has no off-the-shelf Claude Code skill, so it should be written first, as a project skill built with Anthropic's **skill-creator**. That plugin includes evals and benchmarking ([claude-plugins-official](https://raw.githubusercontent.com/anthropics/claude-plugins-official/main/.claude-plugin/marketplace.json)). Its golden test validates the verifier before any model runs. Render a known Three.js trajectory to video, run the DA3 scoring graph on it, and assert errors below threshold. Then perturb the trajectory (wrong direction, half amplitude, a zoom instead of a dolly) and assert that the verifier ranks each perturbation lower. If the verifier cannot separate dolly from zoom on synthetic footage, which is the exact case shotdrift admits it cannot handle, the innovation claim fails. That needs to be known by day three, not day thirteen.

## Conclusion

The gap is real, but it sits one layer above where the claim puts it. Open tools already cover authoring and control rendering, and the ComfyUI ecosystem already has the camera solvers. What nobody has done is point those solvers at the model's *output* and treat the authored trajectory as ground truth. Research has shown the signal works, both as a segment-level training reward and as a test-time selector. Products, Higgsfield included, still leave the user to spot drift and pay for rerolls. That makes the verifier the whole thesis, so the submission should be organised around it: a camera claim the app can check with a number, and a regeneration step that targets only the segment that drifted.

The main strategic risk is timing, not technical feasibility. OmniCam's author, shotdrift's author, or Comfy's own Re-shoot team could each add a "diff the generated camera" node during the build window, and GeoFix is still unread. The safest plan is to make the verifier credible early, using synthetic golden tests that distinguish dolly from zoom, and publish it in a form others can plug in (a V3 node plus a `CS_VERIFIER` adapter). Then the studio is demonstrably the first app built on it rather than another camera-authoring UI. If the dolly zoom passes the verifier, it is the demo's strongest shot. If it fails, showing the verifier catch that failure still supports the innovation claim.
